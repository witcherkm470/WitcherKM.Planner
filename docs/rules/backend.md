# Правила backend-разработки

## Контекст задачи

Перед изменением прочитай только релевантную spec, архитектурный документ и затронутый кодовый срез. Кодовый срез включает изменяемый сценарий и его непосредственные зависимости; не изучай весь solution без необходимости.

При изменении существующей spec используй `git diff` для неё. Если требования конфликтуют с текущей архитектурой или реализацией, сообщи об этом до внесения кода.

## Архитектурные границы

- Следуй Clean Architecture и DDD в текущем виде проекта.
- Инварианты и предметное поведение принадлежат `Domain`.
- Сценарии приложения принадлежат `Application` и следуют существующему CQRS/MediatR-подходу.
- HTTP-адаптация остаётся в `Api`; persistence и EF Core — в `Infrastructure`.
- Не создавай новые межслойные зависимости, паттерны или общие абстракции без spec или ADR.

## Стиль и изменения

- Продолжай существующие соглашения затронутой feature-папки и соседних файлов, а не вводи альтернативный стиль.
- Сохраняй file-scoped namespaces, nullable reference types, `async`/`await`, `CancellationToken` и принятый нейминг.
- Для команд и запросов используй уже принятый в кодовом срезе формат MediatR, Unit of Work и репозиториев.
- Предпочитай имеющиеся `WitcherKM.Common.*` abstractions. Не выдумывай API Common и не дублируй уже существующие возможности.
- При изменении persistent-модели создай новую миграцию; существующие миграции не редактируй.
- Не выполняй рефакторинг, переформатирование или изменение публичного контракта вне требований spec.

После реализации проверь Acceptance Criteria и выполни проверки, релевантные изменению.
