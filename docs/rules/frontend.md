# Правила frontend-разработки

## Контекст задачи

Перед изменением прочитай только релевантную spec, архитектурный и дизайн-документ, а затем затронутый UI-срез. Не изучай весь frontend без необходимости. При изменении существующей spec используй `git diff` для неё.

Если требования конфликтуют с текущим UI, архитектурой, дизайном или доступным backend-контрактом, сообщи об этом до реализации.

## Границы

- Маршрутизация, UI, состояние/оркестрация, HTTP-контракты и SVG остаются в соответствующих текущих каталогах.
- Не помещай HTTP-вызовы, URL и дубли API-моделей в визуальные компоненты.
- Используй существующие endpoint-функции, типы и hooks; не добавляй state manager, UI-kit, CSS framework или иную инфраструктуру без spec.

## Стиль и дизайн

- Продолжай соглашения изменяемого компонента и его соседних файлов: TypeScript, функциональные компоненты, существующий порядок импортов и SCSS Modules.
- Не форматируй и не переписывай несвязанные файлы.
- Соблюдай [дизайн frontend](../design/frontend.md). Если тема не указана, используй текущую тему по умолчанию.
- Сохраняй доступность: семантика, доступные подписи, клавиатурное управление и `:focus-visible`. Для новой анимации учитывай `prefers-reduced-motion`.
- Не меняй backend-контракт и не добавляй продуктовые требования без spec.

После реализации проверь Acceptance Criteria и выполни проверки, релевантные изменению.
