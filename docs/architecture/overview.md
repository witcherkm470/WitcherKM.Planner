# Обзор архитектуры

## Solution

`WitcherKM.Planner.sln` содержит пять проектов:

| Проект | Ответственность |
| --- | --- |
| `WitcherKM.Planner.Domain` | Доменные сущности, их состояния и проверки. |
| `WitcherKM.Planner.Application.Common` | Общие прикладные модели, маппинг и прикладные исключения. |
| `WitcherKM.Planner.Infrastructure` | Контекст данных, EF Core-конфигурации, миграции и репозитории. |
| `WitcherKM.Planner.Application` | Обработчики MediatR-команд и запросов. |
| `WitcherKM.Planner.Api` | Точка запуска, контроллеры, request-модели, настройка сервисов и миграций. |

Тестовый проект WitcherKM.Planner.Tests находится в tests/ и включён в solution дополнительно к пяти production-проектам. Проверки описаны в [testing.md](testing.md).

Отдельно в `scripts/` расположен React-клиент. В `shared/appsettings.json` находится конфигурация, подключаемая API при запуске.

## Контейнерный запуск

`compose.yaml` собирает API из `src/` и локального соседнего репозитория `WitcherKM.Common`,
а статический React-клиент — из `scripts/`. Nginx отдаёт клиент и проксирует `/api/`
во внутренний сервис API. Порт 8080 опубликован только на `127.0.0.1`. Строка подключения в контейнере
указывает на `/data/planner.db`; именованный Docker-том сохраняет SQLite при обновлениях.
Общий `appsettings.json` входит в публикацию API, после его загрузки переменные окружения
имеют приоритет для строки подключения и ключа MediatR.

## Фактические зависимости проектов

```text
Api → Application → Application.Common → Domain
 │       │
 │       └──────────────→ Infrastructure → Application.Common, Domain
 └──────────────────────→ Infrastructure
```

`Application` имеет прямую project reference на `Infrastructure` и использует интерфейсы репозиториев из этого проекта. Это фактическая структура ссылок; документ не утверждает, что она соответствует какой-либо иной целевой архитектуре.

`Infrastructure` использует `Application.Common` для моделей, возвращаемых специальными запросами репозиториев. `Domain` не имеет project references на другие проекты solution.

## Архитектурные принципы

Проект развивается в рамках **Clean Architecture** и **DDD**:

- предметные сущности, состояния и инварианты находятся в `Domain`;
- пользовательские сценарии оформляются в `Application` как команды и запросы;
- HTTP, конфигурация приложения и composition root относятся к `Api`;
- EF Core, миграции и доступ к данным находятся в `Infrastructure`.

При реализации необходимо сохранять эти границы и направление ответственности. При этом нельзя выдавать за отсутствующий факт более строгую изоляцию слоёв: текущая solution содержит прямую ссылку `Application → Infrastructure`, описанную выше. Новые изменения не должны усиливать эту связанность без отдельного архитектурного решения.

## Границы реализации

Пользовательские HTTP-вызовы входят через `Api`, затем передаются обработчикам `Application`. Сохранение данных выполняется через `Infrastructure`. Доменные правила реализуются в предметной модели и вызываются из прикладного слоя.

Структура и назначение внешних библиотек описываются только в пределах их использования в [dependencies/witcherkm-common.md](../dependencies/witcherkm-common.md).
